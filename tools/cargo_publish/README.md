# Cargo publishing inputs

Load `cargo_publish` from `//tools/cargo_publish:defs.bzl`. Declare explicit
package metadata and select a Rust library, named binaries, or both, with sources declared beneath the publishing package directory:

```starlark
cargo_publish(
    name = "publish",
    library = ":library",
    package_name = "example-package",
    version = "0.1.0",
    description = "An example library",
    license = "MIT",
    repository = "https://github.com/LowkeyLab/bazel-repo",
    rust_version = "1.96",
    readme = "README.md",
    package_files = {
        "README.md": "README.md",
        "LICENSE": "LICENSE",
    },
)
```

Run `nix develop --command aspect build //path/to/package:publish_files`.
The outputs are `publish_files.package/` and `publish_files.json` under
`bazel-bin/path/to/package/`. The tree contains the standalone Cargo manifest,
declared Rust sources, and explicitly mapped assets. The JSON generation
contract sits beside the package tree. Cargo doesn't include it as a publishing asset.

Generation uses configured Rust providers and an aspect to obtain selected
production targets, editions, roots, direct dependency aliases, exact versions,
and enabled features. `binaries = {":binary": "cargo-name"}` maps target labels
to published Cargo binary names. Each binary retains its own edition. Optional
`tests = [":unit_test"]` selects test-only direct dependencies as Cargo dev
dependencies. Shared dependencies retain separate normal/dev declarations. The
selected library edge stays inside the package. Test source/runtime wiring is
not staged, and validation doesn't execute selected tests. Generation joins
configured direct dependencies to declared upstream Cargo metadata and the root Cargo manifest and lockfile. Dependency identity
must originate in the root `crates` repository generated by the pinned
`rules_rs` extension, with unambiguous crates.io lock provenance. Requested
default and explicit features reflect configured Bazel activation. The
publisher maintains no separate dependency list or feature overrides.

Generation reads only declared inputs and requires no registry access.
Sources retain paths relative to the publishing package directory. Each
`package_files` label must identify one existing source file, mapped to a
relative package path. Map the required readme, compilation data, and production data explicitly.
Conflicting, reserved, and escaping paths fail with target/path diagnostics.
The generator rejects generated sources, publisher features and build scripts,
compiler flags, environment inputs, separate local packages, and source modifications
requiring Cargo translation. Supported package forms are library-only, binary-only, and combined for
`x86_64-unknown-linux-gnu`. Generation translates configured conditional dependencies when it supports
their active inputs. Unsupported compiler/environment inputs fail explicitly. Upstream crates may use their own Cargo build scripts and
proc macros.

The root Cargo manifest and lockfile remain unchanged. Generation writes no
consumer lockfile and doesn't participate in ordinary Rust compilation.
Cargo owns transitive resolution during the subsequent validation workflow.

## Generation contract

`CargoPublishInfo` is the public analysis provider. `package` is the staged
tree artifact. `contract` is the accompanying JSON file. Validation rules can
consume these fields without discovering source files or reading the checkout.

Contract schema version `1` includes:

- `package`: explicit metadata, edition, and readme path.
- `target`: configured Rust target triple.
- `library`: optional selected label, crate name/type, edition, and staged path.
- `binaries`: selected labels, crate names/types, mapped Cargo names, editions,
  and staged paths.
- `tests`: selected test labels and optional original crate metadata.
- `dependencies`: direct target/package/version/source/checksum identity,
  Cargo alias, dependency kind, enabled feature names, and `default_features`.
- `inputs`: declared package paths, byte lengths, and SHA256 fingerprints.
- `manifest_sha256`: fingerprint of the generated original Cargo manifest.
- `provenance`: fingerprints of the root manifest, lockfile, and module settings.

Identical selected inputs produce identical trees and contracts. The generation
contract describes declared inputs. A later archive validation report must
establish verified package status separately.

The public generation command is `//tools/cargo_publish:generate`. Its required
arguments are `--spec`, `--root-manifest`, `--root-lockfile`, `--module`,
`--output`, and `--contract`. The macro supplies the analysis specification.
Command fixtures exercise rejection diagnostics and deterministic generation
with explicit inputs. Run the offline contract suite with
`nix develop --command aspect test //tools/cargo_publish/...`.

## Archive verification

Run `nix develop --command bazel run //path/to/package:publish` to generate and
validate the package with pinned Cargo/rustc 1.96.0 on the supported Linux x86-64 target. Cargo
first resolves dependencies and runs `cargo package` with package verification
enabled. The validator safely extracts that archive, compares declared source
and asset fingerprints, checks original and normalized manifests, then runs
locked metadata and an explicit locked build for every selected library/binary.
The packaged lockfile must remain unchanged. Direct dependency declarations
retain exact identities, version requirements, aliases, normal/dev kinds,
requested defaults, and explicit features. The report records Cargo's observed
resolved graph and activation separately. Cargo owns additional/transitive
activation. Validation doesn't require equality with Bazel's transitive graph.

Each run writes a private `publish.runs/<run-id>/` directory beneath the Bazel
output directory and prints explicit archive/report paths. It retains command
logs, configuration, metadata, inventory, fingerprints, and phase-specific
failure diagnostics. Success requires all 12 mandatory checks and successful
locked commands covering every production target. Selected Bazel tests provide
dev dependency declarations. They aren't automatically run as Cargo tests.

Pass `-- --offline --registry-cache /path/to/managed/cache` for an offline run.
The cache must already contain all needed crates and index entries. An empty
cache produces a retained Cargo failure report. Online mode permits registry
access. Runs isolate Cargo/compiler configuration from the caller's checkout,
working directory, and ambient environment. In this repository, set the stable
Python cache environment inside Nix for Bazel/Aspect commands:
`nix develop --command env RULES_PYTHON_PYCACHE_DIR=/absolute/stable/python-cache bazel run //path/to/package:publish`.

Consumers depend on the public Rust library `//tools/cargo_publish:report`
(crate `cargo_publish_core`). Call
`validate_verified_archive(report_path, archive_path, destination, expected)`
with explicit paths, a new private destination, and an optional
`ExpectedPackage { name, version }`. It returns a `VerifiedArchive` containing
the validated report, private archive copy, and extracted package root.
`validate_report(&report, expected)` separately checks typed report evidence.
The consumer checks complete target evidence, copies, and hashes the exact
archive, then validates its inventory and declared bytes before returning the
extracted package. Consumers support relocation. The archive SHA256 binds the report to bytes,
while original output paths remain diagnostic.

The offline public command/archive tests exercise failure contracts with
controlled external tools. Explicit publishing commands support
library-only, binary-only, and combined archives, including aliases, normal/dev
and shared dependencies, mixed target editions, nested sources, mapped assets,
and upstream build-script/proc-macro behavior. Identical declared inputs must
produce identical generated trees/contracts. Archives, executables, and fresh
transitive resolution aren't required to be byte-identical.

Generic verification proves supported package generation, declared-input and
direct-dependency fidelity, and pinned package/archive builds. Normal Bazel Rust tests cover app behavior. Authenticated registry upload is a separate
operation.

## Programmatic publishing tests

Publishing tests run in the ordinary Bazel suite:

```sh
nix develop --command aspect test //tools/cargo_publish/... \
  //worktree_pool:publishing_test
```

`rules_testing` checks configured targets and unsupported analysis inputs.
Rust tests using `googletest` cover generated manifests, declared source/asset
bytes, dependency classification, archive/report contracts, and command failures.
Controlled external tools and archive fixtures exercise verification behavior
without registry-backed package installation.

The normal Rust target `//worktree_pool:cli_test` tests command-line behavior
using the Bazel-built executable. CI runs the programmatic tests with formatting,
lint, and coverage. Explicit publishing commands remain available for release
preparation and retain their per-run reports and diagnostics.
