# Cargo constraints for Bazel-staged publishing packages

Research for [Identify Cargo constraints for a Bazel-staged publish package](https://github.com/LowkeyLab/bazel-repo/issues/2143), inspected 2026-10-10. This note supplies constraints for later decisions; it does not choose the publishing rule API or lockfile contract.

## Conclusion and evidence boundary

A generated package must be a complete, independent Cargo source tree with explicit package metadata, target paths, dependency declarations, and a Cargo-valid lockfile. Cargo package verification then checks the archive after normalization. A successful locked package check establishes consistency with the staged Cargo resolution; matching Bazel's dependency resolution requires a separate identity comparison. Exact matching is possible only when the Bazel selection is also a valid Cargo solution for the publishable graph. Direct version pins alone cannot establish that condition. These conclusions combine the Cargo references below with inspection of the existing repository verifier.

The inspected repository commit is `79e850a3fc2d374def76f1f678a2c64d0d96b807`. It pins Rust 1.96.0 and edition 2024; the verifier asserts Cargo/rustc 1.96.0 and Linux x86-64. [Toolchain declaration](https://github.com/LowkeyLab/bazel-repo/blob/79e850a3fc2d374def76f1f678a2c64d0d96b807/MODULE.bazel#L564-L610), [verifier](https://github.com/LowkeyLab/bazel-repo/blob/79e850a3fc2d374def76f1f678a2c64d0d96b807/worktree_pool/install/verify.py).

Cargo references here are the current official documentation retrieved on the inspection date. The versioned 1.96 documentation fetch failed, and the Cargo source request using `rust-1.96.0` returned HTTP 404. Therefore this note does not claim a source audit or execution proof of that exact Cargo release. Implementation must exercise its supported cases with the Bazel-resolved executable, particularly normalized lockfile behavior. This gap does not block identifying the constraints; it leaves version-specific certification to validation.

## Manifest and archive closure

Cargo rewrites the archive manifest, removes workspace/patch/replace tables, includes a lockfile, flattens symlinks, extracts the archive, rebuilds it, and rejects source modification by build scripts. `--no-verify` skips the build proof. `--locked` rejects a missing lockfile or a resolution change; it permits network access. `--frozen` also disables networking. Preserve both the input manifest and normalized output when validating generated files. [Cargo package](https://doc.rust-lang.org/cargo/commands/cargo-package.html).

Target paths are relative to Cargo.toml. Explicit `[lib]` and `[[bin]]` paths allow the repository's flat `lib.rs`/`main.rs` layout; nested layouts and proc-macro/library settings need their own faithful target declarations. Auto-discovery can introduce unintended targets unless controlled. Stage Rust modules and every compile-time included asset at the paths expected by the source. This source-closure requirement is an inference from Cargo's target/path and extracted-build rules. [Cargo targets](https://doc.rust-lang.org/cargo/reference/cargo-targets.html).

An explicit `include` policy avoids dependence on Git ignores or hidden-file defaults. Cargo always excludes nested packages and the root target directory. It always includes Cargo.toml, a minimized lockfile, and a configured license file. Inspect actual archive contents rather than treating a Bazel filegroup as the final archive specification. [Manifest include/exclude](https://doc.rust-lang.org/cargo/reference/manifest.html#the-exclude-and-include-fields).

Workspace-inherited package/dependency values must become concrete in an independent staged manifest; the original workspace shared lockfile and root-only settings do not accompany a detached member automatically. Stage outside the repository's Cargo workspace, or otherwise explicitly isolate workspace discovery. [Cargo workspaces](https://doc.rust-lang.org/cargo/reference/workspaces.html).

Bazel-generated Rust sources can be copied into their expected package paths if they are complete distributable inputs. If code instead expects `OUT_DIR`, a Cargo build script must reproduce those outputs or the source arrangement must change. Build scripts run from the package root, use separate build dependencies, and should write only to OUT_DIR. Native libraries, code generators, environment-dependent configuration, and external tools remain build prerequisites; a Bazel action's effects are not automatically reproduced by Cargo. These are support constraints, not a promise to translate arbitrary actions. [Build scripts](https://doc.rust-lang.org/cargo/reference/build-scripts.html).

## Dependency declarations and feature behavior

The map already requires generated direct dependencies to request the same enabled features as Bazel, including enabled defaults. The existing narrower standalone settings are comparison evidence only; they must not be retained or exposed as per-crate overrides. Package metadata is already assigned to explicit publishing macro attributes. [Plan Bazel-derived Cargo publishing packages](https://github.com/LowkeyLab/bazel-repo/issues/2141).

Preserve dependency aliases/package names, registry identity, version requirements, optionality, requested features, default-feature policy, and normal/build/dev classification. Platform conditions belong in Cargo target tables. Path/git dependencies with a registry version use local sources during development and registry sources when published. Path-only production dependencies cannot be published to crates.io; production dependencies from other registries cannot remain. Local libraries therefore need published crate identities or another explicit packaging strategy. Versionless dev dependencies are removed from published manifests. Build dependencies are separate from normal dependencies and target-specific build dependencies test the host platform. [Specifying dependencies](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html).

Default features are enabled on dependency edges unless explicitly disabled. Disabling defaults on one edge does not cancel features enabled by another edge. Cargo features are additive, including optional-dependency activation and feature forwarding. Resolver 2 avoids merging inactive platform features, host build/proc-macro features with normal features, and dev features with production features unless dev targets are built. Translate Bazel-enabled direct features, including enabled defaults, into Cargo requests, then inspect actual production activation; feature requests and transitive activation remain distinct evidence. [Cargo features](https://doc.rust-lang.org/cargo/reference/features.html).

Cargo lock resolution considers all workspace-member features and all target dependency tables, separately from the features activated for a particular compilation. Existing lock versions are preferred when valid; changed requirements, required features, source identities, Rust-version policy, or incompatible native `links` constraints can invalidate a selection. Edition 2024 defaults to resolver 3, which changes Rust-version preference. Fresh resolution normally prefers newer candidates, and ignores yanked versions unless already locked. Removing other workspace members changes the constraints and opportunities for version unification. [Dependency resolution](https://doc.rust-lang.org/cargo/reference/resolver.html).

## Lockfile generation and exact-version feasibility

`generate-lockfile` is a resolution operation: it creates a lockfile and rebuilds an existing one using current available versions. It is unsuitable as an unconditional preservation check. Offline generation can produce a different result because available cached candidates differ. [Cargo generate-lockfile](https://doc.rust-lang.org/cargo/commands/cargo-generate-lockfile.html).

To preserve a particular valid version selection, Cargo offers targeted `update --precise`; the complete graph still has to satisfy manifest constraints. A root lockfile can be a candidate seed, but it is not inherently a standalone publishing lockfile: workspace entries, source rewrites, checksums, and the staged root must be reconciled. This is an inference about a potential validation route, not selection of a contract or proof that arbitrary Bazel graphs can be exported. [Cargo update](https://doc.rust-lang.org/cargo/commands/cargo-update.html).

Exact direct requirements (`=x.y.z`) leave transitive requirements to their upstream manifests. The inspected files already show the distinction: root Cargo.lock has 763 package identities and worktree_pool/Cargo.lock has 155; ten standalone registry identities do not occur in the root lockfile, including `cc 1.6.0`, `libc 0.2.190`, `insta 1.48.0`, and `syn 3.0.6`. Counts compare `(name, version, source)` triples parsed from both files. This is current snapshot evidence, not a diagnosis of how the drift arose. [Root lockfile](https://github.com/LowkeyLab/bazel-repo/blob/79e850a3fc2d374def76f1f678a2c64d0d96b807/Cargo.lock), [standalone lockfile](https://github.com/LowkeyLab/bazel-repo/blob/79e850a3fc2d374def76f1f678a2c64d0d96b807/worktree_pool/Cargo.lock), [standalone manifest](https://github.com/LowkeyLab/bazel-repo/blob/79e850a3fc2d374def76f1f678a2c64d0d96b807/worktree_pool/Cargo.toml).

A later exactness check must define the relevant graph and compare identities including sources, allowing intentional omission of unrelated workspace packages. Version equality cannot prove matching feature activation. Cargo metadata supplies package identities, dependency kinds/targets, and resolution nodes; target filtering and production feature inspection answer different questions. [Cargo metadata](https://doc.rust-lang.org/cargo/commands/cargo-metadata.html).

For applications, `cargo install --locked` uses the packaged lockfile; ordinary install recomputes dependency selection. A library's lockfile does not constrain downstream consumers' independently resolved application graph. Packaging plus locked installation is therefore useful evidence about source installation, without promising that every consumer uses identical dependencies. [Cargo install](https://doc.rust-lang.org/cargo/commands/cargo-install.html), [Cargo lockfile consumer behavior](https://doc.rust-lang.org/cargo/faq.html#why-have-cargolock-in-version-control).

## Existing acceptance workflow and reuse limits

The Starlark launcher resolves `tc.cargo`, `tc.rustc`, the sysroot and transitive toolchain runfiles. It locates its adjacent runfiles independently of caller CWD. This is reusable pinned-toolchain plumbing. The Python driver uses private Cargo home/build/output directories and strips Cargo/Rust/Python environment overrides. Cargo configuration can also come from ancestor directories and user configuration, so the full environment/configuration boundary still merits validation. [Launcher](https://github.com/LowkeyLab/bazel-repo/blob/79e850a3fc2d374def76f1f678a2c64d0d96b807/worktree_pool/install/verify.bzl), [Cargo configuration](https://doc.rust-lang.org/cargo/reference/config.html).

The package phase performs real locked packaging, extracts the archive safely, checks contents and hashes, checks manifest normalization, records metadata/resolved features, and records a production feature tree. The full phase installs from that extracted artifact and runs application-specific CLI acceptance. Reuse the package evidence boundary; the Git build, executable name and CLI suite remain worktree_pool-specific. The current driver neither asserts equality with the Bazel graph nor supports every Cargo declaration shape. [Verifier](https://github.com/LowkeyLab/bazel-repo/blob/79e850a3fc2d374def76f1f678a2c64d0d96b807/worktree_pool/install/verify.py).

Its staging loop enumerates `manifest.parent`, copies only flat `.rs`/`.md`/Cargo/license/BUILD files, and never consumes the declared package filegroup as an explicit path mapping. A generated manifest in a Bazel output directory will not have source runfiles beside it. Nested sources, generated files, build scripts, assets, and independently located license/readme inputs therefore require explicit staging. The manifest checks cover only top-level normal/dev dependencies, assume exact requirements, and hardcode worktree-pool metadata. This is concrete adjacency evidence for the later packaging design. [Verifier](https://github.com/LowkeyLab/bazel-repo/blob/79e850a3fc2d374def76f1f678a2c64d0d96b807/worktree_pool/install/verify.py), [package inputs](https://github.com/LowkeyLab/bazel-repo/blob/79e850a3fc2d374def76f1f678a2c64d0d96b807/worktree_pool/BUILD.bazel#L132-L148).

## Decisions and validation left to the map

The remaining decisions concern source/path mapping, initially supported target and dependency forms, representation of the already-decided explicit metadata attributes, and whether the standalone lockfile must match Bazel or merely remain valid and stable. Version-specific behavior and unsupported forms need pinned-toolchain acceptance cases after those decisions. Archive verification is local evidence; crates.io performs additional server checks, so it does not certify ownership, name availability, or upload acceptance. No upload is needed to answer this research question. [Publishing](https://doc.rust-lang.org/cargo/reference/publishing.html).

This session inspected sources and compared lockfiles without running Cargo or changing production files. Repository formatting, build, and lint results are recorded in the research ticket resolution; they validate this document branch, not a new package generator.
