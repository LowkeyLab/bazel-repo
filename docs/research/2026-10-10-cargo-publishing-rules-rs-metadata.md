# Cargo publishing metadata at the pinned `rules_rs` revision

Research for [Identify `rules_rs` metadata for Cargo manifest and lock generation](https://github.com/LowkeyLab/bazel-repo/issues/2142), inspected on 2026-10-10. This records available inputs and gaps. The publishing API and lockfile policy remain decisions for later tickets.

## Baseline and conclusion

The repository pins `rules_rs` to `8c2bf39a310c451f862524699191c61345985156`, with a toolchain repository compatibility patch. Its root `crate.from_cargo` consumes `Cargo.toml` and `Cargo.lock`, resolving `wasm32-unknown-unknown` and `x86_64-unknown-linux-gnu`. The root manifest is an aggregate dependency catalog, with a synthetic `workspace` package, normal dependencies, and dev dependencies. Individual Bazel app targets select subsets of that catalog. It's not a Cargo workspace describing those app packages. [Repository module configuration](https://github.com/LowkeyLab/bazel-repo/blob/79e850a3fc2d374def76f1f678a2c64d0d96b807/MODULE.bazel#L172), [Cargo catalog](https://github.com/LowkeyLab/bazel-repo/blob/79e850a3fc2d374def76f1f678a2c64d0d96b807/Cargo.toml), [example Bazel targets](https://github.com/LowkeyLab/bazel-repo/blob/79e850a3fc2d374def76f1f678a2c64d0d96b807/worktree_pool/BUILD.bazel).

**Finding:** the configured Bazel graph is available, but it's insufficient to reconstruct a complete Cargo declaration or standalone lock resolution by itself. Richer information exists in the root manifests, lockfile, registry manifests, and `rules_rs` repository-generation internals. A metadata export could avoid reverse-engineering generated names, but no upstream change is inherently necessary if generation explicitly consumes those existing files. The chosen boundary determines whether generation needs a narrow `rules_rs` export. This conclusion follows from the interfaces compared below.

Consult that revision rather than an unrelated current `rules_rust` provider API. [Reexport](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/rust_library.bzl), [underlying pin](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/rules_rust.bzl).

| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |

Providers are publicly reexported through `@rules_rust//rust:rust_common.bzl`. Their implementation filenames are source citations, not a proposed private loading interface.

Generated registry libraries receive a real `version` attribute and a separate package metadata target with a package URL (`purl`). Library metadata references that target. The package metadata provider holds an output JSON file, not a directly exposed `purl` field. An aspect traversing that target can inspect its `purl` attribute. An action can consume its metadata file. This provides a useful package identity aid, but not a Cargo lock closure or registry checksum. A first-party rule's default `version` isn't evidence of a publishable package version. ## Repository-generation data

The extension runs Cargo metadata with `--no-deps --locked`, parses the Cargo lockfile separately, fetches registry/Git dependency facts, and performs its own feature propagation. It doesn't consume Cargo's full resolved graph. Registry facts preserve feature definitions and dependency declarations, including false default flags, requested features, kinds, aliases, and target conditions. The extension can cache these facts in `MODULE.bazel.lock`. Path facts are reread and deliberately not cached there. Those cached facts are internal extension state, not a publishing API. [Metadata and facts](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/extensions.bzl#L155).

The generated hub's `defs.bzl` offers `all_crate_deps(normal, normal_dev, build, package_name, cargo_only)`, `aliases`, `crate_name`, `edition`, and lint helpers. Here `normal_dev` adds dev dependencies. Combine it with `normal` to include both. `data.bzl` contains dependency label groups and enabled crate features, split into shared and per-platform sets, for Cargo workspace members. It omits requested versions/features/default flags, checksums, source identities, and original target expressions. It describes Cargo members, not every hand-written Bazel target. It's readable generated Starlark data but has no documented publishing compatibility guarantee. [Hub helpers](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/extensions.bzl#L610), [dependency helper semantics](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/private/all_crate_deps.bzl), [data schema](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/private/cargo_workspace_graph.bzl#L676).

Don't infer package identity from a Rust crate name: normalization replaces hyphens, and aliases change linkage names. Versioned hub aliases and generated rule versions help identify selected packages, but package-plus-source identity must come from the lockfile or explicit metadata. The resolver itself indexes package features by name/version. Equal name/version from different sources needs explicit handling in a publishing tool. [Hub aliases](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/extensions.bzl#L510), [resolver indexing](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/private/cargo_workspace_graph.bzl#L383).

## Feature and platform fidelity

The map requires the generated manifest to request the Bazel dependency's enabled feature set, including enabled defaults. Recovering the original publisher request provenance isn't required. The map excludes existing narrower standalone features and per-crate overrides. Missing original edge requests alone therefore doesn't block this enabled-set contract. The distinction below identifies information loss and host/platform fidelity limits.

A requested dependency feature list and its `default-features` flag are declarations. `crate_features` is the propagated enabled set on the dependency. The root catalog requests defaults unless declarations turn them off. `rules_rs` adds `default` for enabled defaults, expands feature definitions, propagates requests, and incorporates annotation features. Consequently, taking a dependency's enabled feature set can't reconstruct which features this particular publisher requested. [Seeding and annotations](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/private/cargo_workspace_graph.bzl#L562), [feature propagation](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/private/resolver.bzl#L122).

**Source-derived limitation:** `rules_rs` stores one `features_enabled[triple]` per package name/version. Incoming normal and build requests update that same set. Workspace dev requests also seed the set. There is no separate host/target or active-dev feature domain in this representation. Cargo resolver 2 separates normal features from build/proc-macro features and inactive dev features. Resolver 3 retains those boundaries. Thus equality of package versions doesn't prove identical Cargo compilation features. [Feature state](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/private/cargo_workspace_graph.bzl#L65), [propagation across dependency kinds](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/private/resolver.bzl#L56), [Cargo feature resolution](https://doc.rust-lang.org/cargo/reference/resolver.html#feature-resolver-version-2).

Build scripts and proc macros execute in the exec configuration. Generated build scripts deliberately select their own features using the target triple while their compilation runs on the host. `platform_triples` must include the union of target and exec triples. The extension evaluates original Cargo `cfg` expressions into the configured platform set, so generated selects can't describe support outside that set. [Build-script feature selection](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/private/rust_crate.bzl#L114), [platform input contract](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/extensions.bzl#L959).

## Inputs for a consistent standalone lockfile

A lockfile candidate needs the selected package's generated manifest, its exact direct package identities, and the authoritative root lock graph: package names, versions, source strings, checksums, and dependency references. Retain original registry identity rather than silently replacing it with a sparse download URL. Git identities include the precise revision. Local package identities require the actual packaged/path layout and versions. The current root lockfile is version 4 and contains registry checksums and version-disambiguated dependency references. It's available as an explicit file input. [Root lockfile](https://github.com/LowkeyLab/bazel-repo/blob/79e850a3fc2d374def76f1f678a2c64d0d96b807/Cargo.lock), [extension lock parsing and registry normalization](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/extensions.bzl#L763), [Cargo lock identities](https://doc.rust-lang.org/cargo/guide/cargo-toml-vs-cargo-lock.html).

The configured build closure isn't necessarily the lock closure. Cargo resolves optional features and platform alternatives beyond the active build. Dropping everything absent from one configured aspect traversal can omit packages required by the standalone manifest. Conversely, the aggregate root catalog includes unrelated packages. Whether to preserve a larger lock, derive a projection, or let Cargo validate a constrained candidate remains undecided. [Cargo lock resolution](https://doc.rust-lang.org/cargo/reference/resolver.html#features).

Failure cases that need an explicit policy or rejection include:

- Unknown dependency kind after rules combine normal/dev/build edges into Bazel `deps`.
- Missing enabled-feature/default information, unsupported platform, or uncertain host feature equivalence. Original request provenance isn't required by the enabled-set contract.
- Multiple versions or sources mistaken for one package because generation retains only normalized crate names.
- Missing checksums, missing source metadata, unresolved local packages, or a manifest incompatible with locked versions.
- Bazel-only extra dependencies, native inputs, build scripts turned off, additive targets, and source patches. In this repo `aws-lc-rs` and `aws-lc-sys` have build scripts off, while `rust-embed-impl` has a source patch. Cargo using unmodified registry sources may behave differently despite matching versions and lock checksums.

These risks follow from the preceding provider omissions, the extension's [validation and local-path checks](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/private/cargo_workspace_graph.bzl#L337), [annotation rendering](https://github.com/hermeticbuild/rules_rs/blob/8c2bf39a310c451f862524699191c61345985156/rs/extensions.bzl#L366), and the [repository annotations](https://github.com/LowkeyLab/bazel-repo/blob/79e850a3fc2d374def76f1f678a2c64d0d96b807/MODULE.bazel#L617).

## Boundary left for the next decision

A publishing rule can consume an explicit manifest/lock metadata file and configured graph without changing `rules_rs`. If the required contract instead demands complete Cargo provenance from target providers alone, the pin lacks that contract: a narrow repository-time export would need source-qualified package identities, checksums, declaration edges, and per-platform resolution data. Such an export would expose existing facts. It would not fix the host/dev feature-domain limitation. This note selects no final provider schema, macro API, lock policy, or unsupported-input policy.
