# Bazel dependency-download cache research

Checked 2026-10-16 for [Investigate download coverage and hosted cache options](https://github.com/LowkeyLab/bazel-repo/issues/2278), part of [Plan Bazel dependency-download caching](https://github.com/LowkeyLab/bazel-repo/issues/2277).

This is research for a later human decision. No cache, credentials, workflow changes, purchases, or acceptance benchmarks were created. Repository facts refer to commit `f40b947479c5705e2ad21df9350014cd21d2e7f2`. Upstream source facts, deductions, and unmeasured outcomes are distinguished below.

## Findings that shape the decision

- Dependency-download persistence is currently off in the pinned setup action. Enabling it is a small integration, but GitHub caches have branch/PR scope and are not an anonymous public download service.
- BuildBuddy and EngFlow support dependency bytes through the Remote Asset API. An ordinary remote action-cache endpoint alone does not enable this. Neither provider's inspected public documentation establishes an anonymous, read-only public namespace meeting this map's complete access policy.
- Bazel 9.3.0 distinguishes downloaded archives from reproducible repository contents. The latter can avoid Git/Go subprocess fetching as well as extraction, but introduces trust in cached repository-rule results and experimental behavior.
- Public object storage can express anonymous GET and trusted publication, but requires a publisher and mirror integration. That trades maintenance for a clearer public-access boundary.

These are trade-offs to discuss, not approval to weaken public reads, change publication policy, or adopt a provider.

## Current repository baseline

[`.bazelversion`](https://github.com/LowkeyLab/bazel-repo/blob/f40b947479c5705e2ad21df9350014cd21d2e7f2/.bazelversion) pins 9.3.0. [`.bazelrc`](https://github.com/LowkeyLab/bazel-repo/blob/f40b947479c5705e2ad21df9350014cd21d2e7f2/.bazelrc) configures BuildBuddy action caching and remote execution. It does not enable a remote download proxy or remote repository-contents cache. Its CI remote timeout is 3,600 seconds, which is unsuitable as an unquestioned dependency-cache outage budget.

A deliberate dependency manifest/key and writer topology are needed. Configuration establishes neither current cache hits nor potential savings.

## Mechanisms and coverage

### Downloaded archives

Bazel's local `--repository_cache` defaults to `{output_user_root}/cache/repos/v1`; it is shared across local workspaces using that root. Downloads with a pinned checksum look up existing bytes before fetching. Cache reads verify their checksum; downloaded bytes are also verified. Mutable metadata without a checksum cannot be assumed reusable by an expected digest. `--distdir` searches local files and validates expected checksums, then permits normal downloading. See Bazel 9.3.0 [repository options](https://github.com/bazelbuild/bazel/blob/9.3.0/src/main/java/com/google/devtools/build/lib/bazel/repository/RepositoryOptions.java), [download manager](https://github.com/bazelbuild/bazel/blob/9.3.0/src/main/java/com/google/devtools/build/lib/bazel/repository/downloader/DownloadManager.java), and [download-cache integrity](https://github.com/bazelbuild/bazel/blob/9.3.0/src/main/java/com/google/devtools/build/lib/bazel/repository/cache/DownloadCache.java).

`--experimental_remote_downloader=grpcs://…` uses Remote Asset `FetchBlob`, then retrieves bytes through CAS. It intercepts Bazel download proxy operations, not arbitrary Git, Go, curl, package-manager subprocesses, Docker pulls, or build/test network access. Bazel sends the expected checksum, verifies returned bytes, and requests fresh content when no checksum exists. File URLs stay local. See pinned [remote download proxy](https://github.com/bazelbuild/bazel/blob/9.3.0/src/main/java/com/google/devtools/build/lib/remote/downloader/GrpcRemoteDownloader.java).

### Repository contents

In 9.3.0, `--repo_contents_cache` defaults to `{repository_cache}/contents`; its default unused-entry GC age is 14 days. Consequently, persisting the entire setup action's repository-cache directory also persists extracted contents by default. An archive-only experiment must explicitly separate or turn off contents caching. See [repository options](https://github.com/bazelbuild/bazel/blob/9.3.0/src/main/java/com/google/devtools/build/lib/bazel/repository/RepositoryOptions.java).

The startup flag `--experimental_remote_repo_contents_cache` defaults off and stores reproducible repository-rule results using the configured remote cache's AC/CAS. It keeps a lazy external filesystem and can skip an entire fetch, including subprocess I/O. Eligibility requires reproducibility metadata, a non-local rule, and safe symlinks. Current 9.3.0 source supports recorded runtime inputs; the initial experimental discussion's older restriction against runtime dependencies is not the current contract. See [startup option](https://github.com/bazelbuild/bazel/blob/9.3.0/src/main/java/com/google/devtools/build/lib/remote/options/RemoteStartupOptions.java), [fetch eligibility/fallback](https://github.com/bazelbuild/bazel/blob/9.3.0/src/main/java/com/google/devtools/build/lib/bazel/repository/RepositoryFetchFunction.java), and [remote contents implementation](https://github.com/bazelbuild/bazel/blob/9.3.0/src/main/java/com/google/devtools/build/lib/remote/RemoteRepoContentsCacheImpl.java).

This is a possible additional mechanism, not proof that existing BuildBuddy configuration caches dependencies. Content digests verify transferred files, but a trusted AC writer determines which result belongs to a repository-rule key. That differs from checking an archive against an independently pinned upstream checksum. Public contents must exclude generated credentials, private material, and sensitive environment-derived outputs.

See GitHub [dependency-cache reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching); BuildBuddy [download proxy guidance](https://www.buildbuddy.io/docs/remote-runner-introduction/#reducing-disk-snapshot-size) and [pricing](https://www.buildbuddy.io/pricing/); EngFlow [Remote Asset setup](https://docs.engflow.com/re/client/remote-asset-api.html), [service options](https://docs.engflow.com/re/config/options.html#experimental_enable_fetch_api), and [pricing](https://www.engflow.com/product/pricing); R2 [pricing](https://developers.cloudflare.com/r2/pricing/) and [public buckets](https://developers.cloudflare.com/r2/buckets/public-buckets/).

R2's `r2.dev` public endpoint is development-only and rate limited; production public access needs a custom domain. R2 is not a drop-in Remote Asset server. Publisher immutability, concurrent create-if-absent behavior, lifecycle deletion, mirror manifests, retries, and lookup telemetry remain implementation work. An archive URL mirror does not automatically cover Git/Go subprocess paths. A `--distdir` bundle adds bulk transfer and filename/manifest management. Inference. evaluate this only if strict anonymous public access outweighs the maintenance preference.

GitHub caches are immutable snapshots. Parallel format/lint/test jobs racing on one key can preserve only one job's snapshot, and PR snapshots cannot seed main. A trusted main warm-up can seed the common baseline. Restored executable contents and marker files require trusted writers; do not archive entire homes, `.bazelrc`, `.netrc`, or credential files. GitHub explains these risks in its [cache reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#best-practices-for-using-caches-securely); its [cache action](https://github.com/actions/cache#usage) offers explicit restore/save operations and timeout controls. Local developers already benefit from Bazel's local cache; GitHub persistence does not itself expose that CI snapshot anonymously to them.

BuildBuddy's inspected [FetchBlob source at `e3306c3`](https://github.com/buildbuddy-io/buildbuddy/blob/e3306c33018452b00ff6832e75bdbb14710c4fec/server/remote_asset/fetch_server/fetch_server.go) checks group/user prefix and CAS/cache-write capability. Read-only callers can reuse a matching cached digest but cannot populate a miss; identical immutable requests are coalesced within the applicable namespace. This is evidence of implementation capability, not proof that the hosted service deploys that revision or offers a public tenant. Avoid inferring anonymous download-cache access from publicly shareable invocation logs.

## Integrity, fallback, and acceptance implications

A remote download proxy needs explicit `--experimental_remote_downloader_local_fallback`: it defaults false in [9.3.0 options](https://github.com/bazelbuild/bazel/blob/9.3.0/src/main/java/com/google/devtools/build/lib/remote/options/RemoteOptions.java). With fallback enabled, failures emit a warning before using the local download proxy. Credentials from netrc/helpers are not propagated by default; keep propagation off for public-only material. URLs and explicitly supplied headers still deserve inspection. The existing global remote header must not accidentally authenticate to a different provider.

Bazel's `--remote_timeout` and retry policy affect remote interactions; this repo's 3,600-second CI override needs a deliberate bounded outage strategy without harming existing remote execution. Repository-contents lookup and upload failures warn and permit fetching, but later lazy-file read failures are a separate outage case to test. GitHub setup restore errors also warn, but its five-minute segment timeout does not satisfy an unspecified total budget automatically. See [remote options](https://github.com/bazelbuild/bazel/blob/9.3.0/src/main/java/com/google/devtools/build/lib/remote/options/RemoteOptions.java), [download proxy](https://github.com/bazelbuild/bazel/blob/9.3.0/src/main/java/com/google/devtools/build/lib/remote/downloader/GrpcRemoteDownloader.java), and [repository fetch](https://github.com/bazelbuild/bazel/blob/9.3.0/src/main/java/com/google/devtools/build/lib/bazel/repository/RepositoryFetchFunction.java).

A scoped inspection of the committed module URLs, Cargo/uv locks, Maven repository setting, and `.npmrc` found public upstream services and no dependency credentials in those inspected declarations. This is not an exhaustive license or distribution-rights audit, nor proof that all transitive/rule-generated material is public. Before public publication, inventory actual fetched URLs and classified paths, exclude credential-bearing/private material, and review redistribution requirements. Do not publish existing machine-wide caches wholesale.

Recommended evidence for the later acceptance decision:

1. Use a fresh runner with empty task-specific local archive/contents/output caches; explicitly record which mechanisms are enabled. A warm local output base cannot prove hosted reuse.
2. Seed a representative target set, then repeat unchanged on another fresh runner. Record fetch phase time, cache bytes/operations, restored snapshot identity, and upstream requests, including Git/Go/metadata bypasses.
3. Correlate Bazel download-cache-hit events or HTTP/gRPC fetch events with provider-side hit/miss and origin-fetch evidence. A successful `FetchBlob` may itself fetch upstream; an action-cache hit or GitHub snapshot hit alone is insufficient.
4. Exercise main, trusted same-repository PR, Renovate, fork restore and fork miss, concurrent writers, dependency changes, eviction, outage, and checksum mismatch. Confirm credential-free forks never obtain publication authority.
5. Separate archive coverage from contents coverage, and establish capacity/bandwidth budgets using observed sizes. No timing, bandwidth, hit-rate, current occupancy, or upstream-request baseline was measured here.

## Questions for the next decision

- Must public reads include anonymous access outside GitHub Actions? If yes, GitHub-only persistence cannot fulfill that boundary; selecting it requires an explicit policy decision.
- Is broader coverage worth experimental repository-contents caching and trusting cached rule results, or should the first specification isolate pinned archive bytes?
- Should BuildBuddy public-read feasibility be confirmed before choosing, or should a managed-storage mirror be considered despite its publisher maintenance?
- What total outage budget and free-tier occupancy/transfer threshold should bound implementation? Provider account settings and live workload evidence remain unknown.
