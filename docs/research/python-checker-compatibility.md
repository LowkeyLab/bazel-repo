# Python checker compatibility and strictness

Research date: 2026-10-17. For [Research Python checker strictness and current-language compatibility](https://github.com/LowkeyLab/bazel-repo/issues/2320), under [Plan strict Python type checking across the repository](https://github.com/LowkeyLab/bazel-repo/issues/2319).

## Scope and evidence

At repository commit `de1b8f8507d476d9c44ef608a1c298bef1b6c055`, `MODULE.bazel` selects Python 3.15. The [accepted Python ADR](../adr/0002-use-rules-py-for-first-party-python.md) requires hermetic Bazel tooling, pytest, Linux x86_64 acceptance, and automatic stable minor upgrades. This note compares checker capabilities; it does not choose a checker or validate a Bazel integration.

Release metadata, documentation, package metadata, and tagged source were inspected. No checker was installed or executed, no representative source was checked, and no compatibility or performance benchmark ran. Supported target versions, usable distributions, and successful execution are separate claims.

## What strict checking actually guarantees

- **mypy:** `strict` checks unannotated bodies and requires complete function annotations, rejects untyped calls/decorators and bare generics, and warns about returning Any. It does not prohibit every Any: `disallow_any_explicit`, `disallow_any_expr`, and `disallow_any_unimported` are separate policy choices. The strict preset can grow between releases. [Current command-line reference](https://mypy.readthedocs.io/en/stable/command_line.html#strict), [dynamic-type options](https://mypy.readthedocs.io/en/stable/command_line.html#disallow-dynamic-typing).
- **Pyright:** strict enables missing-parameter, Unknown-type, and missing-stub diagnostics. Unannotated bodies are analyzed by default; return types may be inferred rather than requiring return annotations. Explicit Any remains an escape hatch. These semantics differ from mypy's annotation contract. [Tagged configuration and strictness table](https://github.com/microsoft/pyright/blob/1.1.414/docs/configuration.md).
- **basedpyright:** retains Pyright's checking model and adds `reportAny`, `reportExplicitAny`, and rule-specific-ignore enforcement. Its recommended/all presets differ from upstream strict; choose and record the intended settings rather than relying on the product name. Recommended mode makes warnings fail the CLI via `failOnWarnings`. [Additional diagnostics](https://docs.basedpyright.com/latest/benefits-over-pyright/new-diagnostic-rules/), [configuration](https://docs.basedpyright.com/latest/configuration/config-files/).
- **ty:** always checks unannotated bodies, but does not require parameter or return annotations. Unknown behaves gradually like Any. Its migration guide proposes explicit ty diagnostics plus existing Ruff's ANN/PYI rules to approximate stricter checking; some checks remain unimplemented. No single `--strict` preset exists. Version 0.0.89 added opt-in return inference for unannotated functions, showing that this behavior is still evolving. [Migration guide](https://docs.astral.sh/ty/coming-from-mypy-or-pyright/), [typing FAQ](https://docs.astral.sh/ty/reference/typing-faq/), [release notes](https://github.com/astral-sh/ty/releases/tag/0.0.89).

For all candidates, a passing check is bounded by configured files, import resolution, stubs, dynamic types, and suppressions. It cannot replace tests. Treat unexplained Any/Unknown and whole-module exclusions as acceptance failures rather than silently weakening policy. This is a proposed acceptance principle, not a claim that every candidate enforces it automatically.

## Tests and dependencies

Pytest's own guidance types fixture return values and test parameters separately, with examples such as `monkeypatch: pytest.MonkeyPatch`; parameterized arguments also need ordinary annotations. Fixture-name injection does not establish a static link between a fixture's output and its consumers. Do not exempt tests wholesale. [Pytest typing guidance](https://docs.pytest.org/en/stable/explanation/types.html).

Mypy needs installed typed packages or stub distributions; ignoring missing imports introduces unchecked Any. Pyright bundles typeshed, supports custom stubs, and can infer incomplete information from library code. ty likewise requires Python source or `.pyi` files for compiled extensions. Pin any additional stub packages with the dependency closure, and test actual import roots rather than assuming the runtime environment automatically supplies the checker's search paths. [Mypy imports](https://mypy.readthedocs.io/en/stable/existing_code.html#fixing-errors-related-to-imports), [Pyright import configuration](https://github.com/microsoft/pyright/blob/1.1.414/docs/configuration.md), [ty import FAQ](https://docs.astral.sh/ty/reference/typing-faq/#why-cant-ty-resolve-my-imports).

## Shortlist and upgrade constraints

Recommended shortlist, pending the separate Bazel-integration investigation:

1. **mypy** for a conventional strict annotation policy and explicit released 3.15 runtime support. Confirm that the chosen Bazel adapter accepts mypy 2.4; the repository's unused `rules_mypy` pin does not establish that compatibility. Trade-offs include interpreter-specific wheel upgrades and incomplete newest typing features.
2. **basedpyright** for inferred returns plus explicit Any diagnostics and a first-party Python distribution. Trade-offs include the Node binary dependency and maintaining a fork-specific policy. **Upstream Pyright** is a viable alternative if its diagnostics suffice and hermetic Node/npm packaging fits the repo better.
3. **ty** remains a conditional alternative if the maintainer accepts a combined ty/Ruff strictness policy and its documented gaps. Native distribution and current 3.15 support are attractive, but parity with another checker's strict preset must not be assumed.

These are research recommendations, not a maintainer decision. No source incompatibility currently rules out all candidates.

For every automatic interpreter update, derive the checker target from the selected repository minor rather than `requires-python`'s lower bound, host Python, or a stale checker default. A checker that accepts a version number can still lack its syntax or standard-library stubs. Validate availability of the locked checker and dependencies on Linux x86_64, imports for every first-party target, and detection of an intentional error in both annotated and unannotated bodies, including tests and CI scripts. Also prove future-target coverage and local/CI failure propagation in the integration work. Checker and stub upgrades need their own reviewed lock changes; a Python upgrade must remain blocked until the required checks pass. These are proposed checks; none ran in this research.
