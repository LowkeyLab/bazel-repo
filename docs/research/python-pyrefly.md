# Pyrefly strictness, Python compatibility, and Bazel integration

Research date: 2026-10-17. For [Research Pyrefly strictness, Python compatibility, and Bazel integration](https://github.com/LowkeyLab/bazel-repo/issues/2324), under [Plan strict Python type checking across the repository](https://github.com/LowkeyLab/bazel-repo/issues/2319).

## Outcome and evidence boundary

Pyrefly deserves consideration alongside mypy and basedpyright: native binaries, configurable strict checking, pytest awareness, and an official Bazel integration. However, the inspected upstream aspect is **not compatible out of the box with the pinned rules_py providers**: its source-discovery fields are empty, and its dependency filtering does not preserve unpacked wheel directories. A successful command that checks no targets would not satisfy the destination.

This is documentation, release-metadata, and source research. No Pyrefly binary, Bazel aspect, type-checking action, or cache-invalidation experiment ran. Python 3.15 version acceptance is established at source level; complete syntax, typing-feature, and stdlib compatibility remains an acceptance gate. No checker is selected here.

The refreshed snapshot is `de1b8f8507d476d9c44ef608a1c298bef1b6c055`. Preserve rules_py, Gazelle, shared uv dependencies, pytest, Ruff, Linux x86_64 acceptance, and automatic stable-minor upgrades. The selected interpreter is 3.15. Earlier research actually queried 13 Python targets, including hidden CI-script packages; this investigation did not repeat that discovery. [Accepted ADR](https://github.com/LowkeyLab/bazel-repo/blob/de1b8f8507d476d9c44ef608a1c298bef1b6c055/docs/adr/0002-use-rules-py-for-first-party-python.md), [existing integration research](https://github.com/LowkeyLab/bazel-repo/blob/d2bd66b803ae60e8ce1301983f40c2137cc2bb9f/docs/research/python-checker-bazel-integration.md).

## Release, distribution, and Python upgrades

The official release API and PyPI identify **Pyrefly 1.4.0**, published October 15, 2026; the release body's internal heading says October 14. Native GNU and musl Linux x86_64 archives have checksum sidecars. The Python package requires Python >=3.8 and publishes `py3-none` platform wheels, including Linux x86_64; its maturin configuration uses binary bindings. A native binary avoids coupling checker execution to the target CPython ABI. Package installation requirements do not establish supported target-language features. Pin artifact and checksum, then verify execution on Linux/Nix. [Release](https://github.com/facebook/pyrefly/releases/tag/1.4.0), [versioned package metadata](https://pypi.org/pypi/pyrefly/1.4.0/json), [released packaging](https://github.com/facebook/pyrefly/blob/1.4.0/pyrefly/pyproject.toml).

Released `PythonVersion::from_str` accepts major/minor/micro values, rejecting versions below 3.5 without an upper bound. Therefore `3.15` is accepted by the model, but accepting arbitrary future versions is weak feature-support evidence. Its fallback is **3.13.0**. Never let that fallback or host Python select the checked version. The release includes ongoing extra-items TypedDict improvements, but the inspected notes do not establish complete Python 3.15 compatibility. Require representative syntax, typing, and version-gated stdlib checks for 3.15 and each later stable minor. [Released version model](https://github.com/facebook/pyrefly/blob/1.4.0/crates/pyrefly_python/src/sys_info.rs), [release changes](https://github.com/facebook/pyrefly/releases/tag/1.4.0).

The Bazel aspect models the target interpreter separately from the checker execution platform and infers its version from rules_python's toolchain unless overridden. Verify parity with rules_py's actual runtime and the shared 3.15 selector. Preserve automatic stable-minor upgrades: compatibility failures should block merging rather than silently check an older version. Review checker updates too; upstream warns that even patches can introduce errors or breaking changes. [Version inference](https://github.com/facebook/rules_pyrefly/blob/05b15bfa440b3d5dc9c1989749a09a52f569ffd3/pyrefly/private/pyrefly.bzl), [version policy](https://github.com/facebook/pyrefly/blob/1.4.0/README.md).

## Strictness and tests

Configured Pyrefly checks unannotated bodies and infers returns by default. Strict enables implicit-Any diagnostics, including missing parameter annotations and bare generic arguments. It **does not require explicit return annotations**: enable `unannotated-return` separately for complete function annotations. `explicit-any`, `no-any-return`, and `unknown-*` are further choices. Strict leaves unknown attribute, variable, and return diagnostics disabled. Record the intended settings; preset names are not interchangeable with mypy or basedpyright. [Released strict-preset assertions](https://github.com/facebook/pyrefly/blob/1.4.0/crates/pyrefly_config/src/config.rs), [released diagnostics/defaults](https://github.com/facebook/pyrefly/blob/1.4.0/crates/pyrefly_config/src/error_kind.rs).

An unconfigured plain invocation can fall back to a limited basic preset. A prospective plain-CLI adapter must configure policy explicitly and disable interpreter discovery while supplying version, platform, and dependency paths. Bazel mode constructs its own configuration and disables interpreter queries and search heuristics. [Configuration](https://pyrefly.org/en/docs/configuration/), [Bazel configuration construction](https://github.com/facebook/pyrefly/blob/1.4.0/pyrefly/lib/commands/bazel_check.rs).

Built-in pytest support needs no plugin. Official docs describe fixture lookup, aliases, navigation, inferred hints, and annotation quick fixes. These aid migration but do not prove every fixture injection or plugin pattern is checked soundly. Retain explicit fixture returns and test-parameter annotations where policy requires; validate built-ins, conftest fixtures, and aliases with negative examples. [Released pytest documentation](https://github.com/facebook/pyrefly/blob/1.4.0/website/docs/pytest.mdx), [pytest annotation guidance](https://docs.pytest.org/en/stable/explanation/types.html).

## Existing Bazel support and compatibility gaps

No Pyrefly registration appears in this repository's module/lock, lint definitions, or tool lock. The pinned rules_lint tree has ty but no Pyrefly aspect. A separate official **facebook/rules_pyrefly** exists: evaluate it before designing fully custom collection logic. The inspected revision is `05b15bfa440b3d5dc9c1989749a09a52f569ffd3`. Upstream calls the interface experimental, targeting Bazel 8/9 and rules_python >=1.7. This repository uses Bazel 9.3.0. [Pinned lint tree](https://github.com/aspect-build/rules_lint/tree/c602583358226de5cad887a3e1887c0c02c9500c/lint), [upstream contract](https://github.com/facebook/rules_pyrefly/blob/05b15bfa440b3d5dc9c1989749a09a52f569ffd3/docs/integration.md), [repository module](https://github.com/LowkeyLab/bazel-repo/blob/de1b8f8507d476d9c44ef608a1c298bef1b6c055/MODULE.bazel).

The aspect traverses `deps`, selects first-party PyInfo targets, and checks their direct owned sources/stubs. It passes accumulated `PyInfo.imports`, repository roots, main-file location, and generated-file overlays to `pyrefly bazel-check`. Dependencies support imports rather than becoming current-target check roots. Default opt-in tags are empty; `no-pyrefly` suppresses checking. [Aspect source](https://github.com/facebook/rules_pyrefly/blob/05b15bfa440b3d5dc9c1989749a09a52f569ffd3/pyrefly/private/pyrefly.bzl).

Two source-level incompatibilities need adaptation while retaining rules_py:

- **Source discovery:** rules_py 1.12.1 libraries populate `transitive_sources`, not `direct_original_sources` or `transitive_original_sources`. The selected rules_python provider defaults the latter fields to empty depsets. Pyrefly reads those original-source fields and skips targets with no direct sources/stubs. Source inference: unchanged upstream integration skips these libraries. Collect authored `ctx.rule.files.srcs` or adapt the provider contract, then verify binaries and wrapped pytest targets too. Shared PyInfo identity alone is insufficient. [Library provider](https://github.com/aspect-build/rules_py/blob/v1.12.1/py/private/py_library.bzl), [provider defaults](https://github.com/bazel-contrib/rules_python/blob/192b1c2dd72d0e42136bcbe6e44ffad0f354d620/python/private/py_info.bzl), [source selection](https://github.com/facebook/rules_pyrefly/blob/05b15bfa440b3d5dc9c1989749a09a52f569ffd3/pyrefly/private/pyrefly.bzl).
- **Wheels and typing metadata:** rules_py wheels expose a directory artifact in `transitive_sources`, containing site-packages and metadata. Pyrefly's aspect reads `transitive_original_sources` and filters by `.py`/`.pyi` extension. Replacing the field alone still discards directories. Preserve declared wheel directories, import roots, stubs, and `py.typed`, then test actual resolution. Upstream defers exact PEP 561 marker visibility and does not model rules_python's venv-symlink layout. Search paths alone do not solve these gaps. [Wheel provider](https://github.com/aspect-build/rules_py/blob/v1.12.1/py/private/py_unpacked_wheel.bzl), [upstream limitations](https://github.com/facebook/rules_pyrefly/blob/05b15bfa440b3d5dc9c1989749a09a52f569ffd3/docs/integration.md).

The toolchain downloads execution-platform archives with SHA-256 validation, defaulting Linux to musl. Its checked-in metadata covers **1.2.0 only**, versus the researched checker 1.4.0. A checksum override or metadata update is needed for 1.4.0, followed by cross-version JSON-contract validation. Do not implicitly downgrade the checker. [Release metadata](https://github.com/facebook/rules_pyrefly/blob/05b15bfa440b3d5dc9c1989749a09a52f569ffd3/pyrefly/private/versions.bzl), [toolchain download](https://github.com/facebook/rules_pyrefly/blob/05b15bfa440b3d5dc9c1989749a09a52f569ffd3/pyrefly/private/toolchain_repo.bzl).

## Configuration, lint enforcement, and cache inputs

**Native Bazel mode does not read pyrefly.toml or pyproject.toml policy.** Preset and diagnostic overrides come from the aspect. Thus the earlier root-pyproject proposal is not directly available here. Choose aspect-owned policy, an explicitly generated shared representation, or a plain-CLI adapter; avoid independently maintained copies. This note chooses none. [Released Bazel guide](https://github.com/facebook/pyrefly/blob/1.4.0/website/docs/bazel.mdx).

Upstream emits the `pyrefly` output group and fails actions on error diagnostics, but lacks rules_lint human/machine reports. Existing `.aspect/config.axl` has an explicit aspect list; CI uses that lint task. Prove a bridge into its requested output groups: appending an aspect alone may schedule no checking actions. A focused rules_lint adapter could reuse checker functionality while adapting providers, inputs, and reporting. A standalone build command does not satisfy the existing-check destination. [Upstream outputs](https://github.com/facebook/rules_pyrefly/blob/05b15bfa440b3d5dc9c1989749a09a52f569ffd3/pyrefly/private/pyrefly.bzl), [lint contract](https://github.com/aspect-build/rules_lint/blob/c602583358226de5cad887a3e1887c0c02c9500c/lint/private/lint_aspect.bzl), [task configuration](https://github.com/LowkeyLab/bazel-repo/blob/de1b8f8507d476d9c44ef608a1c298bef1b6c055/.aspect/config.axl).

Declared inputs include generated JSON, transitive sources/stubs, and executable; policy, version, and platform enter JSON. Changes to declared values participate in Bazel invalidation. The repository adaptation must additionally declare wheel directories, stubs/metadata, and any policy file. Verify invalidation after changes to source, imported dependency, stub, policy, checker, and interpreter selection. None was tested here. [Action declaration](https://github.com/facebook/rules_pyrefly/blob/05b15bfa440b3d5dc9c1989749a09a52f569ffd3/pyrefly/private/pyrefly.bzl).

## Comparison and remaining feasibility evidence

The [earlier checker comparison](https://github.com/LowkeyLab/bazel-repo/blob/dc99de658945f11334969cc81358e9462954f1ff/docs/research/python-checker-compatibility.md) remains useful, with Pyrefly now an additional candidate:

| Candidate              | Main advantage                                                      | Remaining cost or uncertainty                                                               |
| ---------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| mypy                   | Conventional complete-function annotations; documented 3.15 support | Replace outdated checker; verify rules_mypy and lint bridge                                 |
| Pyright / basedpyright | Inference and, for basedpyright, extra Any diagnostics              | Custom Bazel adapter and hermetic Node distribution                                         |
| ty                     | Existing rules_lint reports and native executable                   | Provision actual tool; settle combined strictness policy and gaps                           |
| Pyrefly                | Native binary, pytest awareness, official Bazel-mode import model   | Adapt rules_py source/wheel inputs; bridge reports; verify 3.15 and checker/ruleset pairing |

Before accepting an implementation path, demonstrate:

1. Locked Linux x86_64 execution and representative 3.15 syntax, stdlib and typing behavior, repeated for automatic stable-minor upgrades.
2. Real action coverage of libraries, binaries, wrapped tests, hidden CI scripts, and a new generated target. Compare checked roots with tracked Python; detect empty provider fields, suppressions, and targetless files.
3. Own and transitive imports through both existing roots, a typed wheel, a stub-only package, and pytest fixtures. Prove host-package isolation and that imports retain types rather than degrading to Any.
4. Missing annotations, Any/Unknown leakage, and errors in unannotated bodies fail the agreed policy. Review narrow exceptions without exempting tests wholesale.
5. Type errors fail existing local and CI `aspect lint`, with usable reports and all necessary output groups. Verify each input-invalidation category above.

These are proposed checks, not experiments performed here. The research resolves additional facts without selecting a checker or implementing an annotation migration.
